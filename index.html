A2UI: your design system is now an API for agents.

Nov 25, 20268 min readSwastik Bose

Google's A2UI 1.0, an open protocol for generative UI, lets AI agents answer with real interfaces instead of paragraphs. The catch is the interesting part: an agent can only build with the components you register. Here is what that means for anyone who designs products.

Happening's take

A2UI matters to UI teams less as a protocol and more as a contract. Agents stop replying in paragraphs and start assembling screens, but only from components you have registered and styled, and the app draws them natively on web, iOS, Android and inside assistants like Claude and Gemini. That turns your design system into the interface an AI speaks through: the clearer your components, their descriptions and their states, the better every agent-made screen looks and behaves. Today it earns its place in decision moments, such as approvals, bookings and follow-up questions, not as a replacement for core screens. If you own a design system, start treating it like an API.

    What is A2UI? Agents that answer with interfaces

    On November 11, 2026, Google released A2UI 1.0, the first stable version of its open protocol for generative UI. The idea is simple: instead of replying with text, an agent describes what to show, like a form to confirm or a chart, and the app draws it with its own native components.

    Most coverage treats this as a developer story. It's a design story first. A2UI's central rule is that the agent can only place and configure components the developer has registered. Nothing else gets on screen. That makes the component library the boundary of what an AI can say visually.

    For a decade, design systems kept humans consistent. Now they decide what machines are allowed to show.

    Below: the concept in four interactive pieces, then what it's actually useful for in day-to-day UI work.

    Six messages, or one card

    Google's original A2UI post, from December 2025, opens with a familiar pain. Ask a text-only agent to book a table for two and you get a slow back-and-forth about the day, the time and availability. A form with a date picker, a time selector and a submit button does the same job in one step. Compare the two below.

    How A2UI works: a blueprint, not a webpage

    A2UI is a stream of small JSON messages. In the v1.0 spec, the agent creates a surface, sends components as a flat list where each one has an id and parents point to children by id, then fills a data model that components bind to with JSON Pointer paths (A2UI spec). Because the list is flat and ID-based, the app can start drawing before the whole tree exists. That's exactly what the card at the top does: it's drawn from real v1.0 messages, so the grey placeholders are bindings still waiting for data.

    The return path matters just as much. Inputs write to a local data model straight away, but nothing goes back to the agent until a user action fires. Version 1.0 also adds bidirectional function calls, so a picker can check availability in place (Google). Tap a block below to see what each part does.

    Here is the exact stream behind the booking card at the top of this page. Note what's missing: no colours, no fonts, no spacing. In 1.0 the spec removed built-in theme properties entirely and left styling to each platform's native theme (A2UI spec).

    One message, three brands

    This is the part designers should care about most. Because the agent sends intent and the app owns the pixels, the same message renders natively in whatever design system receives it. Google's pitch puts it plainly: agents use your design system and nothing else (Google). Switch the host below; the JSON on the left never changes.

    Compare that with the older approach of shipping HTML in an iframe. Google's team calls it heavy, visually disjointed from the host and hard to secure (Google). With A2UI the host keeps control of the look, and accessibility comes from the host's native components plus an @accessibility object the agent can fill with labels and descriptions (spec).

    What A2UI is actually useful for in UI work

    Strip away the protocol and A2UI does one thing well: it puts the right small interface in front of someone at the moment they need to decide. These are the six jobs where that pays off, each with a real team already doing it.

    The common thread is moments of decision: assigning, approving, choosing, confirming, reviewing a number. That's where a wall of text fails people and a well-designed card shines. The examples come from Google's 1.0 announcement, its launch post and a2ui.org.

    How your design work changes

    When an agent assembles the screen, nobody draws the final layout. The job moves up a level: you design the parts, the rules and the moments, and let the agent compose within them.

    Your catalog is the vocabulary

    Each component's description goes into the agent's prompt and decides when it gets picked (CopilotKit). Writing those descriptions is now design work.

    Design contracts, not screens

    Define props, bindings, validation and accessibility labels for every component, the way we did for Pay DS. The Basic Catalog's 18 primitives are deliberately sparse, so real products need their own.

    Design every in-between state

    UI streams in as the agent works, and invalid output can fail. Loading order, placeholders and the fallback message are now the main experience, not edge cases.

    Design the commit moment

    Inputs stay local until an action fires. Make that moment obvious: a clear primary button, what will be sent, and what happens next.

    A2UI limitations: the honest caveats

    A2UI is promising, but it's early. A few things to weigh before betting a product on it.

    • Platform support is uneven. Jetpack Compose is still on 0.9.1 with 1.0 "coming soon", and Gemini itself renders 0.9.1 today (Google). The spec page itself now lists 1.0 as current, so the gap is in the renderers, not the protocol.
    • Standards are multiplying: A2UI, MCP Apps, AG-UI, Open-JSON-UI and OpenAI's ChatKit all cover parts of the same ground (a2ui.org). Expect consolidation, and keep your components protocol-agnostic.
    • A protocol doesn't make a good interface. Google's announcement makes no benchmark claims for speed, and an agent can still compose a confusing card from perfectly good parts.
    • Not every screen should be generated. Core workflows that people repeat daily usually deserve hand-crafted, stable layouts; generated UI fits the long tail of one-off decisions.

    The road ahead

    Google's roadmap points at design-system primitives that render natively on every platform and official support for small "decision models" that pick components instead of writing text (Google). Both push in the same direction: the quality of agent-made UI will depend less on the model and more on the system it's allowed to draw with.

    For studios like ours, that's good news. The craft doesn't disappear when agents compose screens. It concentrates in the design system, the component contracts and the moments where a person decides. Teams that treat their design system as a product, with clear names, honest descriptions and well-designed states, will get better AI experiences for free.
